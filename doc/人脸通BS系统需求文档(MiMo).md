# 1 文档说明

## 1.1 编写目的

本文档定义"人脸通 BS 系统"（浏览器/服务端架构，以下简称 BS 系统）的建设需求，作为后续系统设计、开发、测试与验收的依据。BS 系统在完整保留现有 CS 人脸通系统（Delphi 桌面客户端/服务端）的数据结构与业务成果的前提下，把消费、考勤、门禁、订餐、访客等业务改造为浏览器可访问的 Web 系统，实现随时随地使用、集中运维与移动化协同。

本文档同时是 BS 系统与现有 CS 系统、已有 BS 后端工程、硬件通讯服务端、微信端应用之间职责边界的约定文件：哪些能力由 BS 新建、哪些复用既有资产、哪些继续由硬件服务承担，均在本文档中明确。

## 1.2 适用范围与读者

本文档适用于人脸通 BS 系统的产品、设计、开发、测试、实施与运维人员，以及关注既有 CS 系统兼容与平滑过渡的项目干系人。

读者使用本文档时请注意三点：其一，第 5 章"数据库兼容性需求"为强制约束，任何设计不得违反；其二，第 4 章技术栈要求（React + Ant Design / .NET RESTful API / SQL Server）为既定的技术边界；其三，功能需求中各条目的数据来源表名与字段名以第 16 章附录为准，开发时应先核对实际数据库结构再落地。

## 1.5 需求描述约定

需求优先级分为三级：P0 为必做项，缺失将导致系统不可用或违反强制约束；P1 为核心功能项，缺失将影响业务替代完整性；P2 为增强项，可在后期迭代补齐。本文各功能条目默认按 P1 描述，涉及强制约束、资金安全、数据一致性、角色权限的条目按 P0 描述，扩展类条目按 P2 描述。

需求编号规则为 BS-模块-序号（中间以短横线分隔）。本文以章节加编号的方式组织，具体编号在设计阶段细化时可回溯到本章节条目。

文中出现的"不得""必须""禁止"为强制要求，"应""建议"为推荐要求。

# 2 项目背景与建设目标

## 2.1 现状概述

CS 人脸通系统已稳定运行，数据库为 SQL Server，按子系统前缀划分表：ST 60 张、SF 27 张、LH 25 张、KQ 40 张、MJ 50 张、DC 11 张、SK 11 张、XG 28 张，合计约 252 张表，并配套大量存储过程、视图（如 V_XFPsnConsume、V_KQAttendInfo 等）与触发器。各子系统为独立可编译的桌面程序（Attendance.exe、Consume.exe、EatSale.exe、WaterController.exe、STOneCard.exe、AccessControl.exe、Patrol.exe），由主程序壳按角色权限表（ST_SubSystem、ST_RoleRight、ST_MenuInfo）动态拼装菜单并 ShellExecute 启动子程序。

已在建设中的 BS 相关资产有以下几类，现状差异较大：

已有 BS 后端工程 PsnMgrService 存在两个 .NET 版本。.NET Core 版（net9.0）已完成数据访问层建设：使用 EF Core 连接 CS 数据库，脚手架方式全量映射现有表与视图，但业务控制器仅覆盖少量表（人员、卡、部门等）的脚手架级 CRUD，无业务服务层与认证授权；.NET Framework 版（net4.8）已实现面向微信/H5 移动端的成套接口，含人脸采集自动审核、微信支付、订餐、访客等功能。

既有 BS 系统 STCardBS 为 ASP.NET WebForms + 五层手写架构（IDAL/DALFactory/SQLServerDAL/BLL/Model），纯 ADO.NET + 拼接 SQL，覆盖 ST/KQ/MJ/DC/XF，可作为数据访问层与业务规则的参考实现，但不满足本次 React + RESTful 的前后端分离技术栈要求。

硬件侧由独立的消费服务端承担终端通讯与二维码支付，覆盖 5201/5501/5506/5550/5589/8815 等机型与水控终端，业务代码量约数万行。

微信端已面向个人用户提供 H5/小程序能力，覆盖卡管理、充值、消费记录、订餐、考勤申请、门禁记录、访客预约与审批等；CS 数据库已预留微信对接字段（如 ST_Person.OpenID/UnionID/wx_syn_time、XF_Consume.wx_syn_time、VisitorUser.OpenID）并存在 WXUpdate 系列同步触发器。

已有前端骨架工程（PsnMgr(web)、MicroH5 等）已按业务域搭建 React + Ant Design 页面与请求封装，可作为 BS 前端的起点。

## 2.2 建设目标

功能对等：将 CS 的经营/管理功能（消费、考勤、门禁、订餐、访客及卡务、结算等）在 BS 上完整实现，达到业务可替代。

数据同源：BS 与 CS 共用同一 SQL Server 数据库，数据库结构向后兼容，可新增不可删除，CS 与 BS 可并行运行。

体验升级：以 React + Ant Design 提供统一 Web 界面，支持权限化菜单、批量操作、条件查询与报表导出。

移动协同：管理端与个人端（微信 H5/小程序）协同，充值、订餐、申请与审批可移动完成，移动端与管理端数据实时一致。

平滑过渡：BS 与 CS 可并行运行，分模块上线，不影响存量业务与硬件终端。

## 2.3 建设原则

兼容优先：不删除、不改写 CS 既有表、字段、视图、存储过程与触发器；BS 需要的新结构一律以新增方式落地。

复用优先：复用 CS 的存储过程/视图作为数据加工逻辑，复用已有 EF Core 实体与前端骨架，复用既有硬件通讯服务与移动端接口成果，减少重复建设。

边界清晰：BS 负责业务逻辑与人机交互，硬件通讯由既有服务承担，二者通过数据库状态字段与受控接口衔接，BS 不直连硬件。

安全合规：人脸等生物特征数据的使用遵循最小必要原则，充值、挂失、密码修改、人脸采集等关键操作全量留痕。

# 3 总体需求

## 3.1 系统定位与范围

BS 系统定位为人脸通系统的浏览器端业务与管理平台，覆盖以下业务域。

| 业务域 | 对应 CS 子系统 | 需求章节 |
| --- | --- | --- |
| 卡务与核心平台（人员、部门、账户、卡、补贴、结算） | ST | 第 6 章 |
| 消费管理（售饭、灵活消费） | SF、LH | 第 7 章 |
| 考勤管理 | KQ | 第 8 章 |
| 门禁管理 | MJ | 第 9 章 |
| 订餐管理 | DC | 第 10 章 |
| 访客管理 | MJ（Visitor 系列表） | 第 11 章 |
| 水控与巡更（扩展） | SK、XG | 第 12 章 |
| 个人移动端（微信 H5/小程序） | 微信端 | 第 13 章 |

不在本次范围内的事项：硬件终端的固件与通讯协议改造（由消费服务端承担）、微信平台的账号与资质申请、CS 桌面端的功能变更。

## 3.2 用户角色与权限

系统采用"角色—菜单/操作"两级权限模型，角色与权限数据沿用 CS 的角色与权限表（ST_UserInfo、ST_RoleInfo、ST_RoleRight、ST_RightInfo、ST_DeptRight、ST_SubSysRight、ST_MenuInfo）。

| 角色 | 主要职责 | 关键权限范围 |
| --- | --- | --- |
| 系统管理员 | 系统参数、用户与角色、数据维护、日志 | 全部 |
| 卡务/出纳员 | 开户、充值、取款、补贴、销卡、挂失 | 卡务与出纳业务 |
| 消费管理员 | 商品、餐别、终端、键值、纠错 | 消费配置与流水 |
| 考勤管理员 | 班次、规则、排班、异常、报表、账套 | 考勤全部 |
| 门禁管理员 | 控制器、门属性、时段、人员权限、监控 | 门禁全部 |
| 订餐管理员 | 订餐规则、终端、明细汇总、未用餐统计 | 订餐全部 |
| 访客审批人 | 访客预约审批、放行 | 访客审批与记录 |
| 部门主管 | 本部门人员与考勤查询 | 部门数据范围 |
| 个人用户 | 自助查询、充值、订餐、申请、访客预约 | 仅本人数据 |

权限要求：BS 登录用户须与 CS 管理平台操作员表（ST_UserInfo）关联；管理端权限按角色渲染菜单与操作按钮，越权访问返回 403。个人移动端用户不属于管理平台操作员，其身份来自人员表 ST_Person 与账户表 ST_Card，与 ST_UserInfo 无关。

### 3.2.1 角色口径与权限码对照（V2 补充，与布局设计文档统一）

本节为《人脸通 BS 系统-布局与导航及权限控制详细设计文档》（以下简称"布局设计文档"）统一角色与权限口径，两文档不一致处以本节对照关系为准。

## 3.3 总体功能架构

BS 系统在功能上划分为四层。

表现层：React + Ant Design 管理端（PC）与个人端（微信 H5/小程序）。

服务层：.NET RESTful API，按业务域划分控制器与服务，统一鉴权、校验、日志与异常处理。

数据层：SQL Server（复用 CS 库），通过 EF Core 访问既有表，复用既有存储过程与视图。

# 4 技术架构需求

## 4.1 前端需求

框架与组件：采用 React 作为前端框架，Ant Design 作为 UI 组件库；使用统一的路由、状态管理与请求封装，可复用现有工程（MicroH5、PsnMgr(web)）的 utils/request 与 Ant Design Pro 脚手架。

布局与导航：提供登录页与主框架（侧边菜单 + 顶栏 + 面包屑 + 多页签）；菜单按业务域划分为卡务中心、消费管理、考勤管理、门禁管理、订餐管理、访客管理、水控/巡更、报表中心、系统管理。

权限控制：按角色渲染菜单与按钮（操作级权限）；无权限时隐藏或禁用；越权访问返回 403 提示。

通用能力：列表分页/排序/多条件筛选、批量选择与批量操作、表单校验、数据导入导出（Excel）、打印、图表可视化、消息提醒。

兼容性：支持主流浏览器（Chrome、Edge 及同内核浏览器）近两年版本；管理端适配 1366×768 及以上分辨率；移动端适配主流手机屏幕、刘海屏与底部安全区。

交互一致性：统一加载态、空态、错误态与确认提示；危险操作（销卡、注销、清理数据）二次确认。

## 4.2 后端需求

技术栈：ASP.NET Core（.NET 9 为基线，另有 .NET 4.8 同源工程供移动端与历史环境使用），采用 RESTful 风格 API。

分层结构：控制器（Controller）—业务服务（Service）—数据访问（EF Core DbContext/仓储）三层；公共层提供统一返回体、异常处理、日志、参数校验。

| 接口项 | 要求 |
| --- | --- |
| 风格 | RESTful，资源化路径（如 /api/persons、/api/cards/{id}/recharge） |
| 方法 | GET 查询、POST 新增/业务动作、PUT 修改、DELETE 逻辑删除 |
| 返回 | 统一结构 { code, message, data }；分页返回 total/items |
| 文档 | 使用 OpenAPI/Swagger 自动生成接口文档 |
| 版本 | 路径或请求头携带版本号，保证向后兼容 |
| 时间与编码 | 统一 UTC+8 时间与 UTF-8 编码 |

认证与授权：提供登录认证（令牌/会话）与基于角色/操作的授权；管理端对接 CS 的用户角色权限表；移动端采用独立的人员身份校验规则（见 5.6.2）。

数据访问：以 EF Core 映射既有表；对复杂统计复用既有存储过程与视图；写操作使用事务保证资金与记录一致性。

日志与审计：记录接口访问日志、操作日志，记录操作前后值，可查询与导出；移动端接口需有发送与接收日志。

部署形态：支持 Windows/IIS 或 Linux 容器部署，支持多实例与反向代理。

## 4.3 数据库需求

数据库类型：SQL Server（与 CS 一致），字符集与排序规则沿用现有库。

连接与访问：沿用现有连接串配置方式（appsettings 配置），连接串中的口令不得写入代码或文档。

结构管理：新增结构以增量脚本（.SQL）方式提供，按用途分文件（BS_CreateTable.sql 新增表、BS_AlterTable.sql 既有表加列、BS_CreateObject.sql 新增视图/索引/存储过程、BS_InitTable.sql 初始化数据），与 CS 脚本风格保持一致，并按模块分文件。

兼容约束（强制）：见第 5 章。

性能与索引：为高频查询（消费时间、人员、终端、门禁时间、考勤日期）确保必要索引；大批量报表采用存储过程或分批查询。

## 4.4 与硬件通讯服务的对接

BS 不直连硬件终端，硬件通讯全部由 5501 消费服务端及其子服务承担。BS 与硬件服务的衔接方式如下。

| 对接项 | 说明 |
| --- | --- |

| 门禁与人脸终端 | 由消费服务端的人脸门禁子服务与门禁控制器/人脸一体机通讯，另开 TCP 端口供 BS/一卡通客户端连接 |

# 5 数据库兼容性需求（强制约束）

## 5.1 兼容原则

只增不删：BS 系统不得删除、改名或改变 CS 既有表、列、数据类型、约束、索引、视图、存储过程与触发器的定义；不得清空或改写既有业务数据含义。

允许新增：BS 可新增表、新增列、新增索引、新增视图、新增存储过程、新增触发器。

新增列规则：向既有表新增列时，必须允许为空或提供默认值，不得设为 NOT NULL 且无默认值；不得新增与既有列语义冲突的列。

命名规范：新增表以 BS_ 前缀（或按模块 BS_ST_/BS_SF_ 等）命名，避免与 CS 表名冲突；新增列建议以 BS_ 前缀或语义清晰的名称命名，避免重名。

幂等与安全：所有结构脚本必须可重复执行（IF NOT EXISTS 判断），不得包含 DROP/TRUNCATE 既有对象的语句。

回退保障：上线前完成数据库全量备份；变更前提供回退方案。

## 5.6 关键业务数据取数与写入规则（强制）

本节规则直接决定 BS 显示与入账数据的正确性，开发必须遵守。所有涉及人员的表都必须包含 Person_ID 字段作为人员关联键（沿用既有关联方式；BS 如需新增涉及人员的表或列，必须包含 Person_ID）。

### 5.6.1 人员与账户主键规则

人员信息表 ST_Person 以 Person_ID 为主键，Card_No 为卡号，id_number 为身份证号。账户信息表 ST_Card 记录账户资金信息，其中 Card_Balance 为卡（账户）余额，Card_Password 为账户密码，Card_NewDate 为开卡日期，Card_ValidDate 为卡有效期。任何充值成功后，ST_Card.Card_Balance 的值必须相应增加。

### 5.6.2 移动端 Token 校验规则

移动端（H5 端与小程序端）调用后端 API 获取 Token 进行身份校验时，用户名取 ST_Person.Person_No，密码取 ST_Card.Card_Password，二者匹配即通过。该校验与管理平台管理员用户表 ST_UserInfo 无关，移动端用户不得使用 ST_UserInfo 的身份体系。

### 5.6.3 账户绑定与解绑规则

账户绑定：H5 端获取客户 OpenID 后，绑定操作需更新 ST_Person.OpenID 字段；小程序端获取客户 OpenID 后，绑定操作需更新 ST_Person.UnionID 字段。同时必须提供解绑功能，解绑后对应字段清空，原微信标识不再能访问该账户数据。

### 5.6.4 充值入账与日志规则

充值必须改为真实微信支付：采用微信 Native（扫码）/JSAPI（小程序与 H5）下单，支付结果以异步通知入账，并以订单查询作为兜底。实现采用 SKIT.FlurlHttpClient.Wechat.TenpayV2 与 SKIT.FlurlHttpClient.Wechat.TenpayV3 组件。

充值成功后，必须将充值记录写入表 ST_SupplyFund（用户需求中提及的 ST_SuypplyFund 即此表，实际表名为 ST_SupplyFund）；每笔充值无论成功与否都必须在数据库中留下日志记录；后端必须有支付发送与接收的日志记录。

### 5.6.5 门禁通行记录取数规则

门禁通行记录：正常通行记录从表 MJ_NormalRecord 获取，异常通行记录从表 MJ_AbnormRecord 获取；通行方式、异常原因均从表 MJ_EventInfo（按 Event_Code 关联）获取。

### 5.6.6 考勤取数规则

考勤每日取数遵循以下规则。

其一，KQ_Account 表中仅取 Account_Flag 值为 0 的那一条记录；当考勤日期大于该记录的 Date_Bgn 值时，从 KQ_Daily 取每日考勤信息，否则从 KQ_DailyHistory 取每日考勤信息。

其二，执行存储过程 KQ_pd_CalcDaily 会生成每日考勤信息并存入 KQ_Daily。

其三，当需要从 KQ_Daily 获取记录但表中没有该日期记录时，执行存储过程 KQ_pd_CalcDaily 后重新取数。

其四，取最近 3 天的考勤信息时，也先执行存储过程 KQ_pd_CalcDaily，防止打卡记录尚未更新。

其五，涉及表为 KQ_Daily、KQ_DailyHistory，结构见 5.2 与附录 D。班次名称根据 KQ_Class 的 Class_No（班次编号）与 Class_Name（班次名称）获取。

说明：KQ_pd_CalcDaily 为考勤每日计算的存储过程名称，来自用户需求；在现有 4.2 基线 SQL 脚本中未检索到同名过程（基线含 KQ_pd_SynchronizePerson、kq_pd_saverecord8815 等），设计阶段须先确认该过程在目标库中的实际名称与签名后再调用，不得凭空调用不存在的对象。

### 5.6.7 订餐取数规则

食堂信息从表 XF_Area 获取，菜品信息从 XF_WareInfo 获取，菜品类别从 XF_WareType 获取，每日菜品信息从 XF_WareInWeek 获取，餐别信息从 SF_Repast 获取；菜品图片若表 XF_WareInfoPhoto 中有记录则从该表获取，没有则使用默认图片。

订餐扣款模式从 ST_SysParam 中 Param_Code 值为 'DC.Solution' 的行获取：值为 1 为订餐扣款（订餐时扣款），值为 0 为消费扣款（订餐时不扣款，取餐时扣款）。

订餐记录落表规则：订餐模式为订餐扣款时，订餐记录进入 DC_OrderData（字段 Is_WareOrder 标识是否按菜品/菜谱模式订餐）与 DC_OrderDataSub（按菜品订餐才有记录），同时需在消费表 XF_Consume 中增加记录；订餐模式为消费扣款时，订餐记录进入 SF_OrderData 与 SF_OrderDataSub。

菜品订餐多条记录规则：当按菜品订餐且为订餐扣款时，若订了 n 个菜品，需在消费表 XF_Consume 中增加 n 条记录（每个菜品一笔记录）。

### 5.6.8 消费与订餐报表取数规则

消费记录与订餐记录报表需分开显示。消费记录从 XF_Consume 获取，其中 Consume_Time 为消费时间，Consume_Fund 为消费金额，Repast_No 为餐别编号（名称从 SF_Repast 的 Repast_Name 获取），Com_No 为订单号，Card_Balance 为消费后账户余额，MOC_No 为机器编号（机器名称从 ST_MOC 的 MOC_Name 获取）。

订餐记录按 5.6.7 的模式判定分别取自 DC_OrderData/DC_OrderDataSub 或 SF_OrderData/SF_OrderDataSub；两张主表通过 Order_No 关联子表。

### 5.6.9 人脸照片自动审核与压缩存储规则

移动端提交人脸照片后需自动审核（判断人脸照片是否符合要求）。审核通过的照片保存到表 ST_PersonPhoto；若照片大于 80K，需先缩小至 80K 以下再保存到 ST_PersonPhoto。

### 5.6.10 付款码与通行码存储规则

付款码与通行码改为从后端获取（由后端签发，移动端出示）。其签发与核销记录存储于 SK_ScanCode 及 BS_QrCode（如需独立审计），具体存储位置在设计阶段结合 SK_ScanCode 现有结构确认。

### 5.6.11 移动端账户绑定与会话规则（V2 补充，强制）

绑定校验：移动端绑定需输入姓名 + 工号/学号/卡号 + 一卡通查询密码（或手机验证码），与 ST_Person 人员档案匹配后完成绑定（来源：微信端 H5/小程序需求 3.1.2）。

绑定唯一性（强制）：一个微信 openid 仅允许绑定一个有效人员账户；一个人员账户同一时间仅允许被一个 openid（小程序为 unionid）绑定，换绑必须先解绑。解绑后原 openid/unionid 不再能访问账户数据。

授权范围：H5 静默授权（snsapi_base）即可获取 openid；涉及用户昵称、头像等信息的场景使用 snsapi_userinfo 并征得用户同意。

会话有效期：移动端登录态采用服务端会话管理，会话有效期可配置，默认 7 天，到期自动重新授权。校验规则见 5.6.2。

### 5.6.12 充值限额与充值订单状态规则（V2 补充，强制）

金额档位：充值页提供常用金额档位（50/100/200/500 元，可由后台配置）及自定义金额；单笔限额、单日累计限额按平台与微信支付规则执行，超限给出提示（来源：微信端需求 4.2.3）。

订单状态机：充值订单状态为「待支付 / 支付成功待入账 / 已到账 / 已退款 / 已关闭」，全程对用户展示。支付成功但平台入账失败时进入"待处理"状态，由系统自动重试或人工补账；超过约定时限未到账自动触发微信退款并向用户说明。

资金用途约束：充值资金仅用于一脸通账户消费；默认不支持提现；严禁对信用卡套现等违规场景开放。入账与日志规则见 5.6.4。

### 5.6.13 付款码与通行码风控规则（V2 补充，强制）

付款码（来源：微信端需求 4.3.2）：由服务端动态生成，包含加密 token，默认 60 秒自动刷新，截屏、转发无效；付款码与用户账户强绑定，消费机扫码后由平台完成身份核验与扣款。免密额度（单笔免密金额与当日累计免密次数）由平台策略控制，超限需在平台完成密码校验。账户余额不足、账户冻结/挂失、人员离职/离校状态下付款码不可用并展示明确原因。离线码为可选项：按平台风控策略生成有限次离线可用码，联网后自动核销对账。付款码页面超时自动隐藏。存储与签发规则见 5.6.10。

通行码（来源：微信端需求 5.1.2）：由服务端动态签发，含加密身份凭证，默认 60 秒自动刷新，防截屏冒用；开门权限以平台门禁权限组为准，移动端不单独维护权限；人员离职/离校、账户冻结、权限被收回时通行码自动失效。通行结果实时反馈：门点名称、开门时间、通行结果（成功/无权限/超时）。

## 5.7 与 EF Core 实体的对应关系

继续使用 dotnet ef dbcontext scaffold 方式对新增表反向生成实体，采用 --use-database-names 保留数据库原始命名，与既有实体风格一致。

新增表实体放入独立命名空间/目录，避免与既有实体混淆。

对既有表新增列的实体属性，需在实体映射中显式声明（列名、可空性），不得改动既有属性映射。

# 6 功能需求——卡务与核心平台（ST）

卡务与核心平台是所有业务域的基础，BS 需优先建设。本章功能对应用户资料中的"卡务中心/管理系统"章节及其菜单结构（详见附录 B）。

## 6.1 用户、角色与权限管理

操作员信息：新增、修改、注销管理平台操作员，维护编号、姓名、密码、所属部门、附属部门、人员类别。表 ST_UserInfo（User_No、User_Name、User_Pwd、Dept_ID 等）。

角色与权限：定义角色（ST_RoleInfo），为角色分配业务权限（ST_RoleRight）、操作权限（ST_RoleRight/ST_RightInfo）、子系统权限（ST_SubSystem、ST_SubSysRight）、菜单权限（ST_MenuInfo）、设备权限（ST_MOCRight）、部门数据权限（ST_DeptRight）。

权限能力要求。

菜单与操作按钮按角色动态渲染，越权访问返回 403 并记录日志。

支持角色复制，便于快速建立相近角色。

支持"数据范围"控制：全部/本部门/本部门及下级/仅本人。

密码策略：最小长度、复杂度、有效期、首次登录强制修改、连续错误锁定。

关键操作（授权、重置密码、注销）记录操作人与时间。

## 6.2 系统参数与字典

参数维护：按子系统分组维护系统参数（ST_SysParam、XF_SysParam、KQ_SysParam、MJ_SysParam、SK_SysParam、DC 相关参数），支持修改、保存、恢复默认、一键备份与导入。

字典维护：维护数据字典表清单（ST_Dict_Table）、字段清单（ST_Dict_Field）与列表显示配置（ST_Dict_Column）、通用字典项（ST_Dictionary），支持新增业务表后同步登记，保证 CS 与 BS 共用。

人脸与识别相关参数：人脸比对阈值、活体检测开关、验证模式、照片质量与大小阈值（与 5.6.9 的 80K 规则联动）、下发策略。

订餐与消费相关参数：订餐扣款模式（DC.Solution，取值见 5.6.7）、餐别价格、补贴扣除规则、账户余额上限/下限。

## 6.3 部门与人员管理

机构与部门：部门树维护（ST_Department，含部门编号、名称、上级、类别），支持多机构、部门权限与部门排序。

人员档案：人员新增、修改、删除（逻辑删除 Is_Del）、批量导入与导出（Excel 模板）、人员转移部门、人员类别（ST_PersonType）维护。人员关键字段含 Person_ID（主键）、Person_No、Person_Name、Dept_ID、Person_Type、Sex、Birthday、id_number（身份证号）、mobile、Card_No 等。

照片与人脸：人员照片采集与上传、人脸注册（照片入库 + 特征提取 + 索引下发）、照片批量导入、照片自动审核与压缩（见 5.6.9），照片存储于 ST_PersonPhoto。

人员查询：按部门、人员类别、卡号、姓名、工号、身份证号、状态多条件查询；支持分页与导出。

## 6.4 账户与卡管理

账户管理：账户是卡的资金主体，支持 CV 消费账户与 CRM 卡模式的选择，账户资料（ST_Card：Person_ID、Type_No、Card_Password、Card_NewDate、Card_ValidDate、Card_Balance、Card_SmallBalance、Card_State、Subsidy_Fund 等）的查看与修改。

开户与销户：开户（建立人员 — 账户 — 卡号关联）、销户、销卡（可查看余额并处理余款）。

卡业务：挂失、解挂、补卡、换卡、退卡、卡有效期维护、卡密码修改与重置、卡状态查询（正常、挂失、注销、过期）。

账户查询：个人账户余额、消费明细、充值明细、取款明细查询；按部门/人员类别统计账户数、余额、押金。

批量操作：批量开户、批量延期、批量挂失、批量发放补贴，均需二次确认与结果明细。

## 6.5 充值、取款、补贴与出纳

充值：现金/银行卡/微信/支付宝充值录入，写 ST_SupplyFund（Person_ID、Supply_Date、Supply_Fund、Card_Balance、MOC_No、Data_Type、User_No、Remark）并同步增加 ST_Card.Card_Balance；充值成功必须落库，任何情况下均留日志；重复提交须拦截（幂等）。

取款与退费：写 ST_TakeFund/ST_TakeFundHistory，同步扣减账户余额；退款审核。

补贴与调整：补贴发放（按批次/规则）、补贴账户（Subsidy_Fund）与基本账户的区分、补贴扣除规则、账户调整（增加/减少）及原因记录。

报表与凭据：出纳报表（ST_pd_AccountRep、ST_pd_SupplyFundList、ST_pd_TakeFundList）、充值取款凭据打印、转账与账户变更清单（ST_pd_TransferAccountList）。

业务规则。

金额一致性：任何入账必须同时更新账户余额，二者在同一事务内完成。

并发控制：同一账户的写操作必须串行化，避免余额错乱。

全程留痕：操作人、时间、终端、原因、前后余额。

校验：充值金额上限、账户余额上限、重复单据号拦截。

## 6.6 编码与系统维护

编码规则：人员编号、卡号、部门编号、商品编号等编码规则的查看与配置，支持自动生成与手工录入。

数据维护：数据上传（本地到数据库）、数据下载、数据整理（重建索引）、数据清理（按时间清理流水/日志，须二次确认并留备）、数据备份与恢复。

分库/批次支持：对应 CS 的一批/二批数据模式，BS 需明确当前库标识与切换逻辑，避免误操作。

## 6.7 日志查询与审计

日志类型：操作日志、登录/登出日志、系统日志、异常日志、接口调用日志、同步日志。

审计要求：涉及人脸、卡片、账户、权限、充值的操作必须记录操作前后值；提供多条件查询与导出；日志不可被普通角色修改或删除。

新增审计表：BS_OperLog、BS_LoginLog、BS_SyncLog（见 5.4），补充既有日志表不足的字段（前后值、IP、设备信息）。

## 6.8 结算与财务报表

结算类型：出纳结算、账户变更结算、消费结算、补贴结算、订餐结算。

报表范围：账户余额表、预收/应付汇总、充值取款汇总、消费日报/月报、按部门/人员类别汇总、按终端汇总、异常流水清单。

输出要求：支持屏幕查询、Excel/PDF 导出、打印；支持按期间、部门、人员类别、终端筛选；报表口径需与 CS 一致，同一统计维度结果须一致。

## 6.9 系统接口（P2）

对外提供人员、账户、消费、订餐等标准接口，供第三方系统集成；支持人脸识别服务、微信平台、支付渠道、短信服务的配置化管理。

# 7 功能需求——消费管理（SF 售饭 / LH 灵活消费）

## 7.1 基础资料设置

商品管理：商品类别（XF_WareType）与商品（XF_WareInfo：编号、名称、类别、单价、单位、图片、是否启用）维护；商品图片通过 XF_WareInfoPhoto 管理，无图片时使用默认图片。

餐别管理：餐别设置（SF_Repast：餐别编号、名称、起止时间、单价、允许消费次数），支持早/中/晚/夜宵多餐别。

周菜谱：周菜谱与每日菜品维护（XF_WareInWeek、XF_WareOnWeek），供订餐与售卖共用。

消费终端：消费机/售饭机档案维护（ST_MOC：机器编号、名称、型号、参数、所属区域、状态），支持 5201/5501/5506/5550 等型号；终端参数配置与下发。

消费方式与键值：消费方式（定额、自由、菜品、餐别）、终端键值与菜单的下发配置。

折扣与补贴：打折类别（LH_DiscountKind）、时段折扣（LH_TimePartDiscount）、消费区域（LH_ConsumeArea、SK_ConsumeArea）、补贴扣除规则。

## 7.2 消费业务处理

现场与流水：终端消费流水回收与展示（XF_Consume），字段含 Consume_Mode、Consume_Time、Consume_Fund、Before_Fund、Repast_No、Ware_ID、MOC_No、Card_Balance、Data_Type、OrderID、BarCode。

纠错处理：单笔流水纠错（删除、修改金额、改餐别、改终端），纠错必须留痕并同步修正账户余额；重复消费识别与清理（XF_pd_CleanupRepeatConsume）、虚假消费清理（XF_pd_CleanupFakeConsume）。

补助与发放：按规则批量发放补助（XF_pd_CardSupply、XF_pd_CardSupply_Small），支持按人员/部门/人员类别发放，支持小额补助。

消费匹配与缓存：消费数据匹配（XF_pd_ConsumeMatchingAll、XF_pd_ConsumeMatchingPerson）、消费缓存准备与上传（XF_pd_PrepareConsumeCache、XF_pd_UploadConsumeCache）供终端离线/在线使用。

退款与冲正：消费退款、冲正、跨天冲正的处理与审批。

## 7.3 消费明细与汇总报表

明细查询：按人员、卡号、部门、终端、餐别、商品、时间段、消费方式、金额区间多条件查询；支持分页、排序、导出。

汇总报表：按人、按部门、按终端、按商品、按键值、按餐别、按消费方式、按时段（日/周/月）汇总；销售日报与月报；优惠与折扣统计；补助发放与使用统计。

对账与异常：终端流水与库内流水对账、未上传流水监控、异常消费清单（超额、重复、异常时间）。

## 7.5 与硬件通讯服务的边界

BS 负责配置与查询，终端菜单下发、键值下发、充值金额下发、数据回收由消费服务端执行；BS 通过设备状态字段查看下发与回收状态，并提供"强制下发/重新下发"入口触发服务端动作。

离线消费与断网补传场景由服务端保障，BS 需能查询补传结果与差异。

# 8 功能需求——考勤管理（KQ）

## 8.1 规则定义

考勤规则维护：上下班时间、有效刷卡时间范围、迟到早退判定、旷工判定、加班规则、弹性工时、跨天班次规则、节假日与调休设置。

请假类别与额度：请假类别（KQ_LeaveKind）、假期额度与核算方式、请假与销假规则。

考勤规则参数：存储于 KQ_SysParam 等既有参数表，BS 只读/可编辑既有参数，不新建同类参数。

## 8.2 班次设置

班次维护：班次编号（Class_No）、班次名称（Class_Name）、节次（Sect1~Sect5）上下班时间、是否跨天、颜色标识、是否需打卡、适用人员范围。

班次能力：支持一天多个节次、一个班次多段、自由班与固定班、班次复制。

## 8.3 考勤信息与排班

人员考勤资料：KQ_Person（人员考勤编号、班次归属、是否参与考勤、是否需人脸）。

排班与调整：定义班次、调整班次、批量排班、按部门/人员类别排班；相关存储过程 KQ_pd_GetDefineClass、KQ_pd_UpdateDefineClass、KQ_pd_GetAdjustClass、KQ_pd_UpdateAdjustClass、KQ_pd_GetMaxClassNo。

## 8.4 考勤终端

考勤机档案：设备编号、名称、型号、安装位置、所属区域、状态（ST_MOC）。

终端配置与下发：考勤周期、比对方式（人脸/刷卡/指纹）、下发人员与班次；由消费服务端或考勤服务执行下发。

数据回收：打卡记录回收至 KQ_BrushCard，展示回收状态与差异。

## 8.5 考勤数据处理

打卡记录：KQ_BrushCard 查询（人员、时间、设备、方式、图片）。

每日考勤：KQ_Daily（当前账套期间）与 KQ_DailyHistory（历史期间）存储每日考勤结果，关键字段见 5.2 与附录 D。

月度汇总：KQ_Monthly 月度考勤汇总（应出勤、实出勤、缺勤、加班、迟到、早退）。

人员同步：KQ_pd_SynchronizePerson 完成人员与考勤资料同步。

每日计算：执行存储过程 KQ_pd_CalcDaily 生成每日考勤信息并存入 KQ_Daily（强制规则，见 5.6.6）。

## 8.6 考勤异常处理

请假：请假登记必须包含时间段（起始与结束的具体日期时间，例如 2026-11-08 8:30 至 2026-11-08 12:00），写入 KQ_Leave（含 Leave_Hour、Leave_Data、Leave_Name）；支持半天与跨天请假。

批量请假更新：KQ_pd_BatchUpdateLeave。

加班/补签/出差：加班登记与核算、补签申请与审批、出差登记。

异常核对：迟到、早退、缺勤、旷工、未打卡的核对与人工调整，调整必须留痕。

### 8.6.1 移动端考勤申请细则（V2 补充）

补签/申诉：对缺卡、迟到误判等异常记录，可发起补签/申诉：选择日期与时段、填写原因、上传佐证（可选），提交至审批人；审批结果推送通知，通过后由考勤模块修正考勤记录。每月补签次数上限按平台考勤制度执行，超限给出提示（来源：微信端需求 8.3）。

请假申请：请假类型（事假/病假/年假等，按平台 KQ_LeaveKind 配置）、起止时间（必须含具体时间段，见本章 8.6）、时长、事由、附件；提交后按审批流流转；已批准的请假在考勤统计中自动体现；提供"我的申请"列表跟踪在途与历史申请（来源：微信端需求 8.4）。

考勤统计展示：按自然月统计应出勤、实出勤、迟到/早退次数、缺卡次数、请假时长、加班时长；月视图以日历标注出勤、迟到、请假、出差等状态。数据取自 KQ_Monthly 与 5.6.6 的取数结果，移动端只读展示。

## 8.7 考勤报表

报表范围：日考勤表、月考勤表、异常明细（迟到/早退/缺勤/旷工）、加班明细、请假明细与汇总、部门汇总、个人考勤明细（含刷卡时间点与图片）。

输出要求：支持按账套期间、部门、人员、班次、异常类型筛选；支持分页、导出 Excel、打印；报表口径与 CS 一致。

## 8.8 考勤取数与计算规则（强制）

取数规则必须严格按 5.6.6 执行，要点复述如下。

KQ_Account 仅取 Account_Flag 为 0 的唯一记录，以 Date_Bgn 作为账套起算日。

考勤日期大于 Date_Bgn 时从 KQ_Daily 取每日考勤，否则从 KQ_DailyHistory 取。

KQ_Daily 中无对应日期记录时，先执行 KQ_pd_CalcDaily 再取数。

查询最近 3 天考勤时，先执行 KQ_pd_CalcDaily 再取数，避免打卡记录未更新。

班次名称通过 KQ_Class 的 Class_No 与 Class_Name 获取。

KQ_pd_CalcDaily 的名称与签名需在目标库确认后再调用（见 5.6.6 说明）。

## 8.9 移动端考勤联动

移动端提供打卡记录查询、考勤申请（补签、请假，均带时间段）与审批；审批结果回写既有考勤表并触发每日考勤重算（执行 KQ_pd_CalcDaily），确保移动端与管理端结果一致。

## 9.4 远程监控

状态监控：控制器与门在线状态、开门/关门/异常状态实时展示，地图或列表视图。

远程控制：远程开门、常开/常闭、远程关门（MJ_pd_SaveControlInfo、MJ_ControlInfo），操作需二次确认并留痕。

实时事件：报警事件、非法闯入、门长时间未关、胁迫码报警等实时提醒。

## 10.3 订餐扣款与落表规则（强制）

落表规则。

| 扣款模式 | 主表 | 子表 | 是否写消费表 |
| --- | --- | --- | --- |
| 订餐扣款（=1） | DC_OrderData | DC_OrderDataSub（按菜品订餐才有记录） | 需在 XF_Consume 中增加记录 |
| 消费扣款（=0） | SF_OrderData | SF_OrderDataSub | 订餐时不扣款，取餐时按消费处理 |

菜品条数规则：按菜品订餐且为订餐扣款时，订了 n 个菜品需在 XF_Consume 中增加 n 条记录。

关联规则：主表与子表通过 Order_No 关联。

## 10.4 报表与维护

报表：订餐明细（订单号、菜品、餐别、金额、时间）、订餐汇总（按人/部门/餐别/菜品/日期）、未用餐统计、就餐明细、退餐统计、日/月报表。

数据维护：订餐数据清理、异常订餐核对、扣款差异对账。

## 10.5 取数规则与移动端联动

取数规则见 5.6.7（食堂、菜品、类别、每日菜品、餐别、图片默认值）。移动端订餐须与同一后端 API 交互，保证扣款模式与落表规则一致（见 13.5）。

# 11 功能需求——访客管理

凭证与人脸下发：审批通过后生成访客通行凭证（动态二维码，可用于门禁扫码开门/通道闸机）；下发访客人脸至指定门点须访客授权采集人脸；凭证仅在预约时段与授权门点范围内有效，过期自动失效（来源：微信端需求 7.4）。

签离：支持访客签离——被访人或门卫在移动端/终端确认签离，或超时自动签离；超时未离场提醒见本章 11.3。

黑名单：命中平台访客黑名单的登记将被拦截并提示（来源：微信端需求 7.5）。

## 11.4 报表

来访记录明细、被访人接待统计、来访人数与频次统计、超时未离场清单、审批时效统计；支持导出与打印。

# 13 功能需求——移动端（微信 H5 与小程序）

## 13.1 定位与形态

移动端面向个人用户（员工、师生、被访人、访客、审批人），提供自助查询与办理能力，与管理端共享同一后端与数据。

形态一：微信服务号内嵌 H5（MicroH5），通过品牌服务号菜单/消息进入，具备网页授权与支付所需的服务号支付资质。

形态二：微信小程序（MicroH5-miniprogram），独立入口，具备原生体验与支付能力。

后端共用：两端共用统一后端（PsnMgrService 面向移动端的接口集）。现有 H5 与小程序尚未对接后端，本次需完成对接，并提供完整源码与可访问的下载地址。

## 13.2 公共能力

授权登录：H5 端采用微信公众号网页授权（OAuth2.0）获取用户标识；小程序端采用 wx.login + code2session 获取 openid/unionid。

账户绑定与解绑：H5 端绑定需更新 ST_Person.OpenID；小程序端绑定需更新 ST_Person.UnionID；必须提供解绑功能，解绑后清空对应字段并回收访问权限（强制，见 5.6.3）。

Token 校验：移动端获取 Token 时以 ST_Person.Person_No 为用户名、ST_Card.Card_Password 为密码进行校验，与管理平台用户表 ST_UserInfo 无关（强制，见 5.6.2）。

人脸采集：拍摄或上传人脸照片，前端做基本质量校验，提交后端自动审核；审核通过的照片存 ST_PersonPhoto；照片大于 80K 时先压缩至 80K 以下再入库（强制，见 5.6.9）。

消息通知：绑定、审批结果、充值结果、异常提醒通过微信模板消息/订阅消息或短信（阿里云短信）下发。

## 13.3 消费与充值

账户查询：账户余额（ST_Card.Card_Balance）、补贴余额（Subsidy_Fund）、卡状态、有效期。

消费记录：按时间范围查询消费明细（来源 XF_Consume），展示消费时间、金额、餐别名称、终端名称、消费后余额、订单号。

订餐记录：与消费记录分开显示，来源按 5.6.7 的落表模式分别取自 DC_OrderData/Sub 或 SF_OrderData/Sub（强制，见 5.6.8）。

在线充值。

下单：H5 与小程序采用微信 JSAPI 支付，PC 管理端可采用 Native 扫码；实现使用 SKIT.FlurlHttpClient.Wechat.TenpayV2 与 SKIT.FlurlHttpClient.Wechat.TenpayV3。

入账：以微信支付异步通知为准入账，并以订单查询接口作为兜底；入账成功须同时写 ST_SupplyFund 并增加 ST_Card.Card_Balance。

日志：每笔充值无论成功与否均须留数据库日志；后端须记录支付发送与接收日志（强制，见 5.6.4）。

幂等与安全：按订单号防重复入账；金额与订单校验；异常订单人工核对。

取款申请与充值记录：申请提交、状态跟踪、充值/取款记录查询。

## 13.4 付款码与通行码

签发方式：付款码与通行码改为从后端获取（由后端签发，移动端展示），前端不得本地生成（强制，见 5.6.10）。

付款码：动态二维码/条形码，设定有效期与刷新周期；消费机扫码后按账户余额扣款并回写流水。

通行码：个人身份二维码，门禁设备扫码核验后开门；权限校验依据人员门权限与时段。

核销记录：签发与核销记录存储于 SK_ScanCode 以及 BS_QrCode（如需独立审计），支持查询与异常排查。

## 13.5 订餐

查看菜谱：按日期查看每日菜品（XF_WareInWeek）、菜品与价格、图片；无图片时使用默认图片。

订餐与取消：按订餐规则下单与取消；订餐时按扣款模式决定是否即时扣款，并保证落表与消费记录规则正确（见 5.6.7）。

取餐：取餐核销、就餐记录查询。

## 13.6 访客

发起预约：访客或被访人发起预约，填写来访信息与随行人员。

审批：被访人/审批人审批，查看待办与历史。

记录：我的预约、来访记录、状态跟踪、超时提醒、二维码通行凭证。

## 13.7 考勤

打卡记录：查询个人打卡记录与打卡图片。

考勤申请：补签、请假（必须包含具体时间段，例如 2026-11-08 8:30 至 2026-11-08 12:00）、加班、出差申请与撤销。

审批：部门主管/审批人审批，支持批量审批与驳回。

结果与取数：申请通过后回写考勤数据；查询每日/月度考勤时严格按 5.6.6 取数并在必要时执行 KQ_pd_CalcDaily。

## 13.8 个人中心

个人信息：姓名、工号、部门、证件号（脱敏展示）、卡号。

密码与安全：修改账户密码（写 ST_Card.Card_Password）、卡挂失与解挂申请。

消息中心：审批、充值、异常提醒消息列表与已读标记。

解绑与退出：解绑微信标识、退出登录。

## 13.9 与管理端的数据一致性

单一数据源：移动端与管理端均读写同一数据库，不引入独立数据库或中间库。

状态回写：审批、申请、订单结果须回写既有业务表（如考勤、访客、订单表），保证两端查询一致。

冲突处理：同一业务被两端并发操作时以业务规则为准（如订餐取消以扣款状态判定），冲突需可追溯。

### 13.10 移动端页面导航结构（V2 补充）

移动端（H5 与小程序）页面导航结构统一为（来源：微信端 H5/小程序需求 2.4）：

- 首页：功能宫格（充值、付款码、通行码、订餐、菜谱、访客、考勤、人脸采集等）+ 账户余额卡片 + 今日菜谱速览 + 消息通知入口。
- 服务（Tab）：按消费、门禁、订餐、访客、考勤五个模块分组展示全部功能入口。
- 消息（Tab）：系统通知、审批结果、到账提醒、考勤提醒等。
- 我的（Tab）：个人信息、账户余额、卡片管理、设置、意见反馈、帮助中心。

H5 形态通过公众号自定义菜单/消息进入，小程序形态通过小程序码、分享卡片等入口进入；两端功能结构一致，差异仅在登录方式（见 13.2）与绑定字段（OpenID/UnionID，见 5.6.3）。

### 13.11 移动端交互与业务细则（V2 补充）

通用查询与分页（来源 3.4）：所有列表类页面支持下拉刷新、上拉加载分页，默认按时间倒序；记录类查询支持按时间范围筛选（今天/近 7 天/近 30 天/自定义），单次自定义跨度不超过 3 个月；网络异常、接口超时、账户未绑定等场景给出友好提示与重试入口。

人脸采集细则（来源 3.2.3，与 5.6.9 联动）：采集前必须展示《人脸信息处理授权协议》并由用户主动勾选同意；拍照要求正面免冠、五官清晰、无遮挡、光线均匀；服务端质检项为人脸检出、正脸角度、清晰度、亮度、遮挡、是否本人（可选），不合格返回具体原因并允许重拍；每人有效照片数量按平台策略执行（通常 1~3 张）；采集状态为未采集/审核中/已通过/未通过（含原因）；照片传输全程 HTTPS，注销时同步清除。

订餐下单细则（来源 6.2~6.4，与 10.2 联动）：按菜谱订餐采用购物车式确认，支持一次预订多日多餐；按餐别订餐支持批量勾选多日多餐别、按单价汇总扣款；下单时校验订餐截止时间、菜品可订份数、余额是否充足、是否重复订餐；扣款成功后生成取餐凭证（订单号/二维码）；退订截止时间前允许退订，退款原路退回账户余额。

消费记录申诉（来源 4.4）：对异常扣款提供"申诉"入口，提交后流转至管理端处理并反馈结果。

消息订阅（来源 3.3）：充值到账、消费扣款、订餐成功/退订、访客审批结果、考勤异常、人脸审核结果、卡片挂失结果等通过微信模板消息/订阅消息或短信推送；用户可在"我的-消息设置"中按类型开启或关闭。

个人中心细则（来源 9.1~9.4）：挂失需密码或短信验证确认后即时生效，挂失后付款码与实体卡同步停用；解挂、补换卡后自动同步新卡状态；修改密码为原密码校验 + 新密码两次确认，忘记密码走短信验证 + 身份要素校验或人工窗口；意见反馈按分类提交并生成工单；帮助中心提供 FAQ 与客服信息。

# 14 接口需求

## 14.1 RESTful 接口规范

路径与方法：资源化命名，GET 查询、POST 新增/动作、PUT 修改、DELETE 删除；批量操作用独立的批量资源或动作接口。

分页与排序：统一分页参数（page、pageSize）与排序参数（sortField、sortOrder）；分页返回 total 与 items。

返回体：统一结构 { code, message, data }；错误码分级（400 参数、401 未认证、403 未授权、404 不存在、409 冲突、500 服务异常）。

时间与编码：统一 UTC+8、UTF-8；金额以字符串或分为单位的整数传输，避免浮点误差。

文档：OpenAPI/Swagger 自动生成并随版本发布。

## 14.2 认证与 Token 校验规则

管理端：登录认证后颁发令牌，令牌携带用户编号与角色；接口按角色/操作校验权限；令牌有效期与续期策略明确；登出即失效。

移动端（强制）：以 ST_Person.Person_No 为用户名、ST_Card.Card_Password 为密码校验后颁发令牌；与 ST_UserInfo 无关；令牌仅可访问本人数据。

通用要求：令牌存于请求头；敏感接口增加签名、时间戳与防重放；服务端对令牌解析失败统一返回 401。

本文 14.3 的接口清单为 RESTful 目标口径；布局设计文档 9.1 约定前端调用口径；现有后端工程 PsnMgrService(NetCore) 实际路由为 api/[controller] + 动词子路径风格（如 api/auth + login、api/Admin_Order、api/m/access/normal）。三者对照如下，实现与测试以本表为准：

| **业务** | **本文目标口径（14.3）** | **布局设计文档前端口径（9.1）** | **现有后端实际路由** | **说明** |
| --- | --- | --- | --- | --- |
| **管理端登录** | **POST /api/auth/login** | **POST /auth/login** | **api/auth + login** | **一致，前缀 /api 由请求层统一携带** |

## 14.4 微信支付与短信接口

微信支付：使用 SKIT.FlurlHttpClient.Wechat.TenpayV2 与 SKIT.FlurlHttpClient.Wechat.TenpayV3；支持 Native（PC 扫码）、JSAPI（H5/小程序）下单、订单查询、异步通知验签与解密；商户号、证书与密钥通过配置管理，禁止写入代码库。

短信：对接阿里云短信服务，提供验证码下发与校验、模板管理、发送记录与频次限制（见 BS_SmsLog）。

## 14.5 与硬件通讯服务接口

BS 与硬件通讯服务（消费服务端）通过受控方式衔接：设备参数与档案在 BS 维护、由服务端读取并下发；名单与人员下发由 BS 触发、服务端执行并回写状态；消费与门禁记录由服务端写库、BS 读取。

端口、回调地址、WebSocket 端口等服务端参数须从配置读取，不得硬编码（见 4.4）。

## 14.6 与 CS 系统的数据共存与互操作

同库共存：BS 与 CS 共用数据库，双方对同一业务表的写操作需明确职责，避免双写（如消费流水由终端/服务端写，BS 只做纠错）。

同步字段：既有 wx_syn_time、update_time 等同步标记字段须正确维护，避免破坏 CS 的同步逻辑与 WXUpdate 触发器。

触发器与存储过程：BS 若需在既有表上新增触发器，不得覆盖既有触发器，且须评估其对既有触发器逻辑的影响。

事务边界：跨表写操作（如充值同时写 ST_SupplyFund 与 ST_Card）必须同一事务，失败整体回滚。

# 15 需求优先级与实施分期

## 15.1 分期原则

先基础后业务：先完成登录、权限、人员、账户等基础能力，再建设各业务域。

先管理端后移动端：管理端先行，移动端在接口与管理端能力稳定后对接。

复用优先、逐步替换：优先复用已有后端工程（EF Core 数据层、移动端接口实现）与前端骨架，避免重写。

可并行上线：各业务域可独立上线，与 CS 并行运行互不影响。

## 15.2 实施分期

| 阶段 | 范围 | 关键交付 | 依赖 |
| --- | --- | --- | --- |
| 阶段一 基础平台 | 登录认证、角色权限、人员与部门、系统参数与字典、日志与审计 | 可登录、可管人、可审计的 BS 基础框架 | 既有角色权限表、增量脚本 |
| 阶段二 卡务与资金 | 账户与卡管理、充值取款、补贴、出纳结算与财务报表 | 资金业务闭环（含微信支付入账） | 阶段一、微信支付与短信配置 |
| 阶段三 消费与订餐 | 消费基础资料、消费流水与纠错、汇总报表、订餐与扣款落表 | 消费与订餐业务替代 | 阶段二、硬件通讯服务 |
| 阶段四 考勤、门禁与访客 | 班次与规则、排班、考勤计算与报表、门禁权限与记录、访客预约审批 | 考勤门禁访客业务替代 | 阶段一、硬件与识别服务 |
| 阶段五 移动端与扩展 | H5/小程序对接后端、充值、付款码/通行码、订餐、访客、考勤、水控与巡更 | 移动端可用、扩展业务上线 | 阶段二至四接口稳定 |

## 15.3 优先级清单

P0（强制、必须满足）：数据库只增不删的兼容约束；充值入账同时写 ST_SupplyFund 与 Card_Balance；每笔充值留日志与后端收发日志；移动端 Token 校验规则（Person_No + Card_Password，与 ST_UserInfo 无关）；账户绑定/解绑写 OpenID/UnionID；付款码与通行码由后端签发；涉及人员的表必须含 Person_ID；门禁记录取数来源（MJ_NormalRecord/MJ_AbnormRecord/MJ_EventInfo）；考勤取数规则（KQ_Account 唯一记录、KQ_Daily/KQ_DailyHistory 分界、KQ_pd_CalcDaily 先算后取）；订餐扣款模式与落表规则；人脸照片自动审核与 80K 压缩。

P1（核心替代能力）：人员与部门、账户与卡、消费流水与报表、考勤排班与报表、门禁权限与监控、访客预约审批、移动端查询与办理。

P2（增强）：水控与巡更、系统对外接口、报表模板定制、消息中心深度定制。
